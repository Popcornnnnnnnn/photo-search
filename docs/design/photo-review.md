# Review photos

The sidebar's **Review photos** entry offers conservative cleanup candidates. Users can keep an image or explicitly delete its original from Apple Photos after confirmation. Nothing is automatically deleted. Deletion marks remain reviewable and never execute in the background.

## Candidate selection

The first version reads current annotations whose input hash matches the available asset. It does not run a model or re-index the library. Captions indicating severe whole-scene blur, an obstructed lens, or blurry close-ups of the ground/feet can become candidates. Generic blur, blurred backgrounds, white backgrounds, and blank fields in documents are insufficient.

Blank-image suggestions require both a matching caption and an almost uniform neutral, very light or very dark local preview, with no recognized OCR text. Unreadable files are skipped, never treated as blank. This uses a local preview, so the original should still be checked before deciding to delete.

This is a deliberately limited rule-based first pass. It can miss images with incomplete descriptions or over-select an intentional blurred image. It is not a calibrated quality score, does not infer personal value, and does not compare neighboring shots. The manually reviewed ten-image discussion sample informed the boundary; its eight accepted candidates are not hardcoded into the app or pre-marked.

## Review and storage

The screen reuses the library's `PhotoGrid`, `PhotoCard`, `PhotoOneUpView`, and `PhotoInspector`, including keyboard/trackpad navigation, zoom, and image information. Compact **To review** and **Kept** filters replace the separate list layout. **To delete** contains explicitly marked photos. Pending photos can be marked for a batch or deleted individually. **Keep** advances selection; **Review again** reverses it. Closing returns to the existing library/search state; locating explicitly opens its timeline position.

Decisions persist in the app's preferences by asset ID and content hash. Changed content becomes pending again. Refresh reads the latest index and skips stale annotations. No schema changes or additional model dependencies are introduced.

## Explicit deletion

**Delete all N…** on the **To delete** list confirms a snapshot of all marked photos, excluding kept and pending items, and submits them in one PhotoKit change transaction. A missing or non-deletable original rejects the batch before submission. Successful deletion updates the index together; cancellation/failure preserves the whole list. **Delete…** identifies the selected filename and explains that the original will be deleted from Apple Photos, including iCloud-synced devices when enabled. Apple Photos normally retains deleted items in Recently Deleted for 30 days. The main app requests PhotoKit read/write permission only after confirmation; the export helper's existing grant is separate.

Only sources with verified PhotoKit local identifiers (`apple-photos`, `apple-photos-full`, `apple-photos-benchmark`) can be deleted here. File imports and `apple-photos-selection` exports have no verified mapping and show a disabled action. Before calling PhotoKit, the current database identity, content hash, and availability must still match. PhotoKit must find the exact original and allow deletion.

Cancellation, denied access, missing originals, or a rejected change leave the index and candidate untouched. After PhotoKit reports success, only the matching asset is marked unavailable in the local index, removed from review, and the library reloads. Search and subsequent random browsing exclude unavailable assets. Cached previews and other source files are not deleted. A failed local update after successful Photos deletion is reported as an index-refresh problem, not a failed deletion. The ordinary library sync reconciles it later. Recovering an original in Photos is reflected after that sync.

## Validation

Tests cover the caption boundary, neutral blank pixels versus documents/colored images, stale annotations, OCR exclusion, unreadable images, persistent and reversible decisions, content changes, and unchanged source files. Deletion tests inject a fake Photos operation against temporary indexes: exact identity, success, cancellation, denied permission, missing originals, stale content, unsupported sources, and an index write failure after successful deletion. Real-window validation covers the shared grid/viewer, Keep/review again, and the deletion confirmation with Cancel. Actual user photos must not be deleted as a test.
